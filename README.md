# ProjectDB Order Management API

A Spring Boot REST API for managing categories, products and orders using the existing `project-db` MariaDB database.

## Technologies

- Java 17
- Spring Boot 3.5.16
- Spring Web
- Spring Data JPA
- Jakarta Bean Validation
- MariaDB
- Maven

## Setup and running

The application requires the existing `project-db` database and its tables. Hibernate does not create or modify the schema because `spring.jpa.hibernate.ddl-auto=none`.

Configure these environment variables in the IntelliJ run configuration:

- `DB_USERNAME`: the dedicated API database username, `projectdb_api`
- `DB_PASSWORD`: the password assigned to that account

The application connects to:

`jdbc:mariadb://127.0.0.1:3306/project-db`

Run `com.example.projectdb.ProjectdbApiApplication`.

Base URL: `http://localhost:8080`

Build and package the application:

```powershell
mvn clean verify
```

## REST endpoints

Requests and responses use JSON. POST and PUT requests should include `Content-Type: application/json`.

### Categories

| Method | Endpoint | Purpose | Successful response |
|---|---|---|---|
| GET | `/api/categories` | List categories | 200, category array |
| GET | `/api/categories/{id}` | Read one category | 200, category |
| GET | `/api/categories/{id}/products` | List products in a category | 200, product array |
| POST | `/api/categories` | Create a category, optionally with products | 201, created category |
| PUT | `/api/categories/{id}` | Update category name and description | 200, updated category |
| DELETE | `/api/categories/{id}` | Delete an empty category | 204, no body |

Example category creation request:

```json
{
  "name": "Test Category",
  "description": "Example category",
  "products": []
}
```

The `products` list is required but may be empty. Nested products use the product request fields below, with `categoryId` omitted because they belong to the new category.

Example category response:

```json
{
  "id": 12,
  "name": "Test Category",
  "description": "Example category"
}
```

The ID is generated by the database; the example ID is illustrative.

Category updates accept `name` and `description` only. The name is required and cannot exceed 100 characters.

A missing category returns 404. Deleting a category containing products returns 409 Conflict.

### Products

| Method | Endpoint | Purpose | Successful response |
|---|---|---|---|
| GET | `/api/products` | List products | 200, product array |
| GET | `/api/products/{id}` | Read one product | 200, product |
| POST | `/api/products` | Create a product | 201, created product |
| PUT | `/api/products/{id}` | Update product fields | 200, updated product |
| DELETE | `/api/products/{id}` | Delete a product | 204, no body |

Example product creation or update request:

```json
{
  "name": "Test Product",
  "description": "Example product",
  "price": 19.99,
  "stockQuantity": 10,
  "categoryId": 1,
  "supplierId": null
}
```

Example product response:

```json
{
  "id": 1004,
  "name": "Test Product",
  "description": "Example product",
  "price": 19.99,
  "stockQuantity": 10,
  "categoryId": 1,
  "supplierId": null
}
```

Product validation:

- Name is required and cannot exceed 255 characters.
- Price is required, nonnegative, and allows up to eight integer digits and two decimal places.
- Stock quantity is required and nonnegative.
- Category and supplier IDs are optional, but must be positive when supplied.
- A supplied category ID must identify an existing category.

A missing product returns 404. An invalid category returns 400. Database foreign keys prevent deletion of products referenced by order items; the controller does not currently translate this failure into a specific conflict response.

### Orders

| Method | Endpoint | Purpose | Successful response |
|---|---|---|---|
| POST | `/api/orders` | Create an order with items | 201, order with items and total |
| GET | `/api/orders/{id}` | Read an order | 200, order with items and total |
| PUT | `/api/orders/{id}` | Update status and delivery date | 200, updated order |
| DELETE | `/api/orders/{id}` | Delete an order and its items | 204, no body |

Example order creation request:

```json
{
  "customerId": 1,
  "shippingAddressId": null,
  "items": [
    {
      "productId": 1,
      "quantity": 2
    },
    {
      "productId": 2,
      "quantity": 1
    }
  ]
}
```

Order creation checks:

- Customer ID is required, positive, and must exist.
- An optional shipping address must belong to the customer.
- At least one item is required.
- Product IDs and quantities must be positive.
- Products must exist and cannot appear twice in the same order.
- Unit prices are copied from the product records when the order is created.
- New orders receive status `NEW`.

Example response from the manual order test:

```json
{
  "id": 200001,
  "customerId": 1,
  "orderDate": "2026-10-08T20:20:11",
  "deliveryDate": null,
  "shippingAddressId": null,
  "status": "NEW",
  "items": [
    {
      "id": {
        "orderId": 200001,
        "productId": 1
      },
      "quantity": 2,
      "unitPrice": 22.22
    },
    {
      "id": {
        "orderId": 200001,
        "productId": 2
      },
      "quantity": 1,
      "unitPrice": 546.08
    }
  ],
  "total": 590.52
}
```

The total is calculated with `BigDecimal` as the sum of quantity multiplied by unit price. IDs, dates and prices depend on the database.

Example order update request:

```json
{
  "status": "PROCESSING",
  "deliveryDate": null
}
```

Allowed statuses are `NEW`, `PROCESSING`, `SHIPPED` and `CANCELLED`. Delivery date cannot be before the order date. Updates change status and delivery date only; they do not change order items. No status-transition rules are enforced.

Missing orders return 404. Invalid requests return 400. POST responses include a `Location` header identifying the created resource.

## Database relationships

- Products may belong to a category.
- Orders reference customers and optionally shipping addresses.
- Order items reference orders and products.
- Order items use the composite primary key `(order_id, product_id)`.
- Foreign keys protect the relationships.

## Database features

### View

`customer_order_view` joins customers and orders, exposing customer name, email, order dates and status.

The view was checked using orders belonging to customer 1. It is currently queried through SQL, rather than a dedicated API endpoint.

### Trigger and status history

The `log_order_status_change` trigger records changes to order status in `order_status_log`.

Each entry contains the order ID, old status, new status and change timestamp. The trigger uses a null-safe comparison to avoid logging unchanged statuses.

A test update from `NEW` to `PROCESSING` produced a log entry. Audit entries remain after an order is deleted because the log table has no foreign key to orders.

### Index

`idx_orders_status` indexes the order status column.

An `EXPLAIN` query filtering orders by `PROCESSING` showed that MariaDB selected this index. This verifies index use, rather than providing a performance benchmark.

### Transactions

Order creation and deletion use `@Transactional`.

Order creation saves the order and its items as one transaction. If a product does not exist, the operation rolls back.

A rollback test submitted a valid product followed by a nonexistent product. The API returned 400, and order and order-item counts remained unchanged.

Order deletion removes the items before deleting the order within one transaction.

### Scheduled snapshots and time-related data

The `daily_order_status_summary` event saves a timestamped snapshot into `order_status_summary` every day.

It records counts of orders currently marked `NEW`, `SHIPPED` and `CANCELLED`, plus the total count of all orders. These are snapshots of current statuses, not counts of orders created that day. Other statuses are included in the total only.

The event scheduler was enabled, and automatic execution was verified by a new summary row dated `2026-10-08 21:27:16`.

The MariaDB server must be running with `event_scheduler=ON` for automatic execution. The runtime setting should be checked after server restarts.

Order dates, delivery dates, timestamped status logs and summary snapshots provide time-related information. System-versioned temporal tables are not implemented.

## Database security

The application uses the dedicated `projectdb_api` database account.

| Tables | Granted permissions |
|---|---|
| `productcategories`, `products`, `orders`, `orderitems` | SELECT, INSERT, UPDATE, DELETE |
| `customers`, `customeraddresses` | SELECT |

Database credentials are supplied through environment variables rather than stored in source code.

Customer and address lookup queries use SQL parameters. Request DTOs use Bean Validation.

The trigger and scheduled event use their configured database definer account. The API account does not manage these database objects.

Database account permissions protect database access; the REST API itself currently has no authentication or authorization.

## Verification

Manual checks confirmed:

- Category create, read, update and delete.
- Product create, read, update and delete.
- Order creation with items and a calculated total.
- Order read, status update and deletion.
- Status-change trigger logging.
- Removal of order items when deleting an order.
- 404 responses after deleting test resources.
- Transaction rollback for a nonexistent product.
- Customer-order view results.
- Selection of the status index by the query planner.
- Automatic scheduled summary insertion.
- Category CRUD after switching database credentials.
- Rejection of status `ABC` with 400; the saved order status remained `NEW`.

`mvn clean verify` completed with `BUILD SUCCESS` and produced an executable JAR. The build output did not show automated tests running; the checks above were performed manually.

## Current limitations

- There is no order-list endpoint.
- Category and product list endpoints are not paginated.
- Order items are created, read and deleted through orders; separate item-update endpoints are not implemented.
- Order creation does not check or reduce product stock.
- Supplier existence is not checked by the product controller.
- Database constraint errors are not consistently translated into friendly API responses.
- The API has no authentication or authorization.
